# UBOR-JAVA R02 — интеграция WPILib

## Статус выпуска

В R01 WPILib не использовался. R02 добавляет **исходный код физического backend на WPILib 2026.2.1** в существующий симулятор, а не отдельный несвязанный пример.

**Сборка и запуск WPILib в этой среде НЕ выполнены.** Здесь отсутствует Maven, а загрузка библиотек из frcmaven.wpi.edu недоступна. Поэтому в архиве нет готового исполняемого WPILib-дистрибутива. `software/dist/ubor-sim.jar` — заново собранный и проверенный LEGACY_FIRST_ORDER, а не WPILib.

Проверено здесь: 50 проверок ядра/legacy-интеграции, 20 проверок границы сменной физики с явно обозначенной тестовой моделью, 9 проверок параметров; реальный TCP/HMAC loopback с 40 ответами и отключением после разрыва. Парсер Java проверил синтаксис 37 исходников. Это НЕ полная компиляция WPILib.

## Запуск WPILib на компьютере

Нужны **Java 21, Maven 3.9+ и доступ к Maven Central / FRCMaven**. Первый запуск скачивает настоящие библиотеки. Сначала открыть терминал в каталоге `software`:

```text
mvn -Pwpilib clean verify
```

Команда компилирует ядро, приложение и robot-wpilib, распаковывает нативные библиотеки и запускает WPILib-проверки отдельной JVM. Профиль `full` с Pi4J/DL4J для этих тестов не требуется.

Windows:
```text
run-wpilib.cmd --about
run-wpilib.cmd --desktop --nt
run-wpilib.cmd --demo ..\verification\my-wpilib-demo 90
```

Linux:
```text
./run-wpilib.sh --about
./run-wpilib.sh --desktop --nt
./run-wpilib.sh --demo ../verification/my-wpilib-demo 90
```

Сценарий `--about` должен реально инициализировать HAL и вывести источник WPILib JAR. Отсутствующие зависимости/ошибки JNI не замалчиваются и не переключают программу на старую модель. `run-simulator.cmd/.sh` теперь направляют именно в WPILib; для прежней модели сохранены `run-legacy-simulator.cmd/.sh`.

В пульте: **Physical ARM (SIM)**, затем **Arm / Disarm**, затем удерживать **SPACE**. Стрелки/WASD — движение; C — ручной подбор с выбранной меткой. AUTO использует известные координаты и метки сцены, **не нейросеть**. После аварийного останова требуется восстановить условие, сбросить программную защёлку и снова разрешить физическую цепь.

## Что изменено

`SimDynamics` отделяет физику от сцены. `WpilibDynamics` вызывает настоящие `DifferentialDrivetrainSim`, два `DCMotorSim` и `BatterySim`; `WpiSensors` записывает и считывает HAL-энкодеры, аналоговые и цифровые входы. В этом пути Simulator НЕ интегрирует движение сам: поза, скорости, пройденный путь, токи и напряжение приходят от backend.

```text
Пульт Java / TCP + HMAC
        -> RobotService -> SafetyController -> DriveControl
        -> Simulator -> WpilibDynamics
        -> DifferentialDrivetrainSim + DCMotorSim + BatterySim
        -> EncoderSim / AnalogInputSim / DIOSim / RoboRioSim
        -> Sensors -> SafetyController / DriveControl
```

`WpiDashboard` публикует Field2d и телеметрию через NT4 (только loopback). Подключение Glass: 127.0.0.1:5810; объект `SmartDashboard/UBOR/Field`. Это канал наблюдения, не разрешение управления моторами. Зависимости Java и нативные ZIP зафиксированы в `robot-wpilib/pom.xml`.

Параметры модели вынесены в `software/config/wpilib-sim.properties`. Масса 30 кг, радиус колеса 0,1 м, колея 0,5 м; инерция, сопротивление батареи и характеристики моторов — **допущения до измерений**, не паспорт конкретных покупных узлов. Геометрия колёс должна соответствовать DriveControl.

## Границы

WPILib не моделирует изгиб щетины, трение и деформацию мусора, 3D-контакты, схему MOSFET/DRV8874, исполнение Raspberry Pi или машинное зрение. Перенос предмета остаётся геометрическим автоматом, но теперь зависит от скоростей щётки и ленты. Из него убрана ошибочная проверка класса предмета: опасный предмет тоже физически можно подобрать, если ошибётся управляющая логика.

Аппаратный робот по-прежнему использует Pi4J, а HAL WPILib — только настольный симулятор. Гироскоп здесь виртуальный диагностический датчик, не добавленный в электрическую схему IMU. Реальная аварийная цепь и безопасный тормозной путь не подтверждены программными тестами.
